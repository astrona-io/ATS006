Test your understanding of `tar` compression filters, forced compression levels, content-listing verification, `--listed-incremental` backup mechanics, and restore validation.

## Scenario-Based Questions

### Question 1
You need to create a new gzip-compressed archive `export.tar.gz` from a directory of files, and the task explicitly requires the **strongest possible compression**. You run `tar -czf export.tar.gz /data/reports` and it completes without error. What is wrong with this approach?
*   **A)** Nothing — `-z` always compresses at gzip's maximum level by default.
*   **B)** `-z` invokes gzip with its default compression level (6), not the maximum level (9); `-z` alone provides no way to pass a compression-level flag through.
*   **C)** `tar -czf` cannot create gzip archives at all; only `--use-compress-program` can.
*   **D)** The command fails silently and produces a corrupt archive whenever `-z` is combined with a directory instead of a single file.

<details>
<summary><b>Reveal Correct Answer & Teacher's Explanation</b></summary>

**Correct Answer: B**

*   **Why B is correct:** The `-z` flag is a shortcut that simply pipes `tar`'s archive stream through `gzip` using gzip's own default settings — compression level 6. It exposes no syntax for passing `-9` or any other level through. To force maximum compression you need `tar --use-compress-program="gzip -9" -cf export.tar.gz /data/reports` (or, less durably, the `GZIP=-9` environment variable). The command in the scenario "succeeds" but silently does not satisfy the "strongest possible compression" requirement.
*   **Why others are incorrect:**
    *   *Option A* is incorrect because gzip's own default level is 6, a middle-ground setting, not its maximum level 9.
    *   *Option C* is incorrect because `tar -czf` absolutely can create valid gzip archives — it just can't control the compression level while doing so.
    *   *Option D* is incorrect because `-z` with a directory target works fine and produces a valid, if not maximally compressed, archive.
</details>

### Question 2
You are converting `data.tar.bz2` to `data.tar.gz` and want to prove the two archives contain exactly the same set of files. You run:
```bash
tar -tjf data.tar.bz2 > list1.txt
tar -tzf data.tar.gz  > list2.txt
diff list1.txt list2.txt
```
`diff` reports many lines as different, even though you're confident every file was carried over correctly. What is the most likely explanation?
*   **A)** `tar -t` cannot list gzip archives, so `list2.txt` is empty.
*   **B)** The two listings are in different internal orderings (the order entries were written into each archive), and neither list was sorted before comparing.
*   **C)** `diff` cannot compare two text files that were generated by different `tar` invocations.
*   **D)** The bzip2 archive is corrupted, which is why the lists don't match.

<details>
<summary><b>Reveal Correct Answer & Teacher's Explanation</b></summary>

**Correct Answer: B**

*   **Why B is correct:** `tar -t` prints archive entries in the order they were physically written, which commonly differs between two independently created archives of "the same" content — one might enumerate a subdirectory's files before its siblings, the other after. Without piping both listings through `sort` before comparing, `diff` will report what looks like a mismatch purely due to ordering, even when the actual file sets are identical. The fix is `tar -tjf data.tar.bz2 | sort > list1.txt` and the equivalent for the gzip archive.
*   **Why others are incorrect:**
    *   *Option A* is incorrect because modern GNU `tar` lists gzip archives fine with `-tzf` (and often auto-detects the format even without `-z`).
    *   *Option C* is incorrect because `diff` compares file content line-by-line regardless of which command produced each file — the mismatch here is caused by ordering, not tooling incompatibility.
    *   *Option D* is incorrect because there is no evidence of corruption in the scenario, and unsorted-listing order differences are a far more common and much simpler explanation.
</details>

### Question 3
You are backing up `/srv/app` with `sudo tar -czpf backup.tar.gz --exclude=<pattern> /srv/app` (archiving the absolute path directly, with no `-C`), and need to exclude a subdirectory named `cache` that exists at `/srv/app/cache`. You also happen to know there is an unrelated directory named `cache` deep inside a vendored dependency at `/srv/app/vendor/lib/cache` that you want to **keep** in the backup. Which `--exclude` usage achieves exactly this?
*   **A)** `--exclude=cache`
*   **B)** `--exclude=/srv/app/cache`
*   **C)** `--exclude=*/cache/*`
*   **D)** `--exclude-from=cache`

<details>
<summary><b>Reveal Correct Answer & Teacher's Explanation</b></summary>

**Correct Answer: B**

*   **Why B is correct:** `--exclude` patterns are matched against the path as it's stored in the archive. Since this invocation archives `/srv/app` directly with no `-C`, the stored paths are absolute, so `--exclude=/srv/app/cache` matches that one exact path and leaves any other directory that happens to also be named `cache` elsewhere in the tree untouched. This is precisely what's needed since the vendored `cache` directory must be preserved. (Note: if `-C` were used to `cd` before archiving a relative path instead, the stored paths — and therefore the exclude pattern — would need to be relative too, without the leading slash.)
*   **Why others are incorrect:**
    *   *Option A* is incorrect because a bare name pattern like `cache` matches that name at *every* level `tar` walks, which would also exclude `/srv/app/vendor/lib/cache` — exactly the directory the scenario wants kept.
    *   *Option C* is incorrect because a glob like `*/cache/*` matches *contents inside* any `cache` directory at any depth, again including the vendored one, and it wouldn't actually exclude the `cache` directory entry itself, only files beneath it.
    *   *Option D* is incorrect because `--exclude-from` expects a *file* containing a list of patterns, not a pattern itself; passing `cache` as the argument would make `tar` try to read a file literally named `cache` for exclusion patterns.
</details>

### Question 4
You've been running nightly `tar --listed-incremental=/backup/state.snar` backups for weeks. Last night's cleanup script accidentally deleted `/backup/state.snar`. Tonight's incremental backup job runs using the exact same command line as always, against the same snapshot path, and completes with exit status 0. What actually happened?
*   **A)** The job failed silently and produced an empty, unusable archive.
*   **B)** `tar` detected the missing snapshot file, raised a warning, and skipped the run entirely.
*   **C)** With no snapshot file to compare against, `tar` had no baseline, so it silently performed a full backup instead of an incremental one, then created a brand-new snapshot file as the new baseline.
*   **D)** `tar` automatically recovered the missing snapshot's contents from the archive's own internal metadata.

<details>
<summary><b>Reveal Correct Answer & Teacher's Explanation</b></summary>

**Correct Answer: C**

*   **Why C is correct:** The snapshot file *is* the incremental mechanism — it's the only record of what's already been backed up. With it gone, `tar` has nothing to compare the current filesystem state against, so it falls back to archiving everything, exactly like a level-0 (full) backup, and this happens with no error or warning. It then writes a fresh snapshot file to serve as the new baseline going forward. This is the single most important failure mode to know cold for `--listed-incremental`: losing the snapshot silently breaks the "incremental" property without breaking the exit code.
*   **Why others are incorrect:**
    *   *Option A* is incorrect because the resulting archive is a valid, complete (if unexpectedly large) full backup, not an empty or broken one.
    *   *Option B* is incorrect because `tar` does not detect this condition as an error state at all — no warning is raised.
    *   *Option D* is incorrect because there is no mechanism for `tar` to reconstruct incremental-tracking metadata from a plain archive; the snapshot file's information is not duplicated anywhere else.
</details>

### Question 5
After restoring a full `tar` backup of `/etc` into a scratch directory with `sudo tar -xzpf backup.tar.gz -C /restore`, you run `diff -r /etc /restore/etc` and it reports no differences at all. Can you conclude the restore fully preserved the original file permissions and ownership as well as content?
*   **A)** Yes — an empty `diff -r` output guarantees content, permissions, and ownership are all identical.
*   **B)** No — `diff -r` compares file content by default; it does not check permission bits or ownership, so a permissions/ownership regression could exist even with empty `diff -r` output.
*   **C)** No — `diff -r` cannot be used on directories containing hidden (dotfile) entries, so the comparison is incomplete regardless.
*   **D)** Yes, but only if the `-p` flag was also passed to `diff -r` during the backup step.

<details>
<summary><b>Reveal Correct Answer & Teacher's Explanation</b></summary>

**Correct Answer: B**

*   **Why B is correct:** `diff -r` recursively compares file *content* between two directory trees and reports files that differ or exist on only one side — it does not, by default, compare permission bits, ownership, or other metadata. A restore could have every file's byte content perfectly intact while still having lost or altered permissions (for example, if `-p` was omitted during backup or restore), and `diff -r` alone would report a clean, empty result regardless. Verifying permission/ownership fidelity requires a separate explicit check, such as comparing `stat` or `ls -l` output on a file whose mode bits actually matter (like `/etc/shadow`).
*   **Why others are incorrect:**
    *   *Option A* is incorrect because it overstates what `diff -r` checks — content equality is not the same claim as full metadata equality.
    *   *Option C* is incorrect because `diff -r` does compare hidden/dotfile entries by default; that is not a limitation of the tool.
    *   *Option D* is incorrect because `diff` has no `-p` flag with that meaning, and permission preservation is controlled by `tar`'s own `-p`/`--preserve-permissions` flag at backup and restore time, not by anything passed to `diff`.
</details>
